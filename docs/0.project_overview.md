# 42 Overflow

## 1. Vision

42 Overflow is a secure, multi-user web platform designed to enhance collaborative learning within the 42 Network.

While the official Intra focuses on administrative tracking, 42 Overflow shifts the emphasis toward:

- Peer-to-peer knowledge sharing
- Real-time communication
- Structured technical discussions
- Secure and scalable system design

The goal is to provide a production-grade, microservices-based platform that demonstrates both collaborative features and advanced engineering practices.

---

## 2. Problem Statement

Students at 42 often rely on fragmented communication channels (Slack, Discord, private chats) to discuss projects and share solutions. These channels lack:

- Structured knowledge indexing
- Quality control mechanisms
- Persistent, project-specific discussion threads
- Unified identity and access control

42 Overflow addresses this gap by integrating:

- Project-based discussion forums
- Real-time friend-based chat
- Secure authentication
- Advanced permission management
- Production-level security practices

---

## 3. Core Objectives

### 3.1 Functional Objectives

- Enable secure authentication via OAuth providers.
- Provide project-specific discussion boards with voting mechanisms.
- Support real-time, friend-based messaging using WebSockets.
- Maintain persistent chat and forum history.
- Enforce role-based access control (Student/Admin).

### 3.2 Technical Objectives

- Implement a microservices architecture.
- Enforce HTTPS everywhere.
- Secure internal service communication via mTLS.
- Implement rate limiting and request validation at the gateway layer.
- Integrate monitoring and metrics collection.
- Ensure multi-user concurrency without race conditions.

---

## 4. System Architecture Overview

### Entry Layer

- Nginx as reverse proxy and TLS termination point.
- Secure external access via HTTPS.

### Gateway Layer

- Quarkus-based API Gateway.
- Centralized authentication and JWT validation.
- Redis-backed rate limiting (token bucket model).
- Structured logging and metrics instrumentation.
- Filtering and validation of incoming requests.
- SSE upgrade handling.

### Microservices

- **Auth Service**: Login and OAuth integration, JWT issuance, user management, and role assignments.
- **Forum Service**: Project-based threaded discussions with voting and markdown support.
- **Chat Service**: Real-time messaging with presence tracking and message persistence.

### Data Layer

- PostgreSQL for persistent storage of user data, forum posts, and chat messages.
- Redis for caching and rate limiting.

### Observability

- Prometheus for metrics scraping
- Grafana for monitoring dashboards

### Security

- mTLS for inter-service communication.
- WAF/ModSecurity for request hardening. **TODO: TBD**
- Secrets managed via Vault. (e.g., database credentials, API keys) **TODO: TBD**
- Zero-trust principles applied throughout the architecture.
- Strict input validation on both frontend and backend to prevent injection attacks.
- Comprehensive logging of authentication attempts, access patterns, and potential security incidents.
- Role-based access control to ensure users can only access resources and perform actions appropriate to their permissions.
