# 42 Overflow

## Project Overview

42 Overflow is a secure social and collaborative platform built for the 42 Network. It combines structured technical discussion, direct user interaction, and production-style platform engineering in a single web application.

The project is designed around a simple product goal:

- give 42 students a better place to discuss projects, connect with peers, and exchange knowledge in a secure multi-user environment

Instead of focusing on administrative tracking, 42 Overflow emphasizes:

- user profiles and identity
- friendships and direct messaging
- project-focused forum discussions
- secure backend boundaries
- operational visibility through monitoring

---

## Product Type

42 Overflow fits the subject's **social and collaborative platform** direction.

In practice, the product combines:

- a social layer: profiles, friendships, direct messaging, and presence
- a collaborative layer: project-based discussions, replies, and voting
- a platform layer: secure gateway routing, internal service trust, and observability

## Core User Value

42 Overflow is intended to help students:

- find and connect with other users

## Architecture Summary

42 Overflow is implemented as a microservices-based web platform.

### Entry Layer

- **Nginx** handles external HTTPS ingress and forwards traffic to internal services.

### Gateway Layer

- **Gateway Service (Quarkus)** centralizes:
  - request routing
  - cookie-JWT authentication
  - role-based access control
  - rate limiting
  - request policy checks
  - metrics and structured logging

### Application Services

- **Auth Service (Quarkus)** for identity, login flows, user management, and token issuance
- **Forum Service (FastAPI)** for posts, replies, and discussion features
- **Chat Service (Go)** for direct messaging, presence, and realtime communication
- **Web Service (Next.js)** for the frontend application and SSR delivery

### Data and Support Services

- **PostgreSQL** for persistent application data
- **Redis** for gateway rate limiting
- **Prometheus** for metrics collection
- **Grafana** for operational dashboards and alert visibility

## Security Model

The project follows a zero-trust-minded service design.

Key security properties include:

- HTTPS for external access
- mTLS on internal service paths that require mutual trust
- JWT validation at the gateway layer
- backend-enforced role-based access control
- request filtering and rate limiting at the gateway
- input validation on both frontend and backend
- secrets kept out of version control through local environment configuration
