# Technical Decisions

## Purpose

This document captures the current implementation-facing technical decisions behind 42 Overflow. It focuses on the stack choices, integration patterns, and practical conventions that shape the codebase as it exists today.

---

## 1. Frontend Technology

The frontend is implemented with **Next.js 15** and **TypeScript**.

This choice was made to support:

- SSR where it improves delivery and routing behavior
- a modern React-based developer experience
- strong type safety in the frontend
- a structured application layout for multi-feature product work

The frontend is delivered as its own service and communicates with backend functionality through the gateway rather than directly binding to each backend service from the browser.

---

## 2. Frontend Styling and UI Approach

The web application uses **Tailwind CSS** for styling.

This supports:

- fast iteration on UI layout and responsiveness
- consistent utility-based styling across the frontend
- easier collaboration in a multi-page application

The frontend also uses reusable UI components and shared feature-level organization rather than placing all UI logic in route files.

---

## 3. Backend Language Split

42 Overflow uses different backend technologies for different service domains:

- **Quarkus / Java** for the gateway and auth services
- **FastAPI / Python** for the forum service
- **Go** for the chat service

This was not chosen for novelty alone. Each service reflects a practical tradeoff:

- Quarkus is well suited to structured service layers, JWT-aware gateway logic, and container deployment
- FastAPI is productive for forum-style CRUD and schema-driven request handling
- Go is well suited to direct network handling and chat-oriented runtime behavior

The result is a polyglot backend with clear boundaries rather than a single-language stack forced into every role.

---

## 4. Gateway as the Browser-Facing API Layer

The browser does not call internal services directly.

Instead, the gateway acts as the browser-facing API layer and provides:

- centralized route dispatch
- request classification by path family
- authentication and RBAC checks
- request-policy validation
- rate limiting
- standardized downstream execution behavior

This decision reduces duplicated edge logic across services and gives the system a single place to evolve policy behavior.

---

## 5. JWT and Cookie-Based Authentication

The platform uses JWT-backed authentication with browser-facing cookie handling at the gateway layer.

This allows the system to:

- keep authentication state tied to backend validation rather than frontend trust
- resolve user identity before protected requests reach business services
- preserve stateless validation behavior for downstream access control

The trusted identity context forwarded internally is normalized by the gateway rather than re-derived independently by every service.

---

## 6. REST-First Service Communication

The current service-to-service and browser-to-backend model is primarily REST-based.

That applies to:

- auth flows
- forum operations
- friendship and chat management flows
- most normal product requests

Realtime behavior is handled separately where required. The architecture does not force all communication into a queue or event-bus model when the main product flows are better served by direct request/response interfaces.

---

## 7. Realtime Chat Behavior

The chat portion of the product includes realtime client behavior for messaging and presence-related updates.

The implementation supports long-lived communication behavior while keeping the rest of the product in normal web request form. This avoids overcomplicating unrelated services while still satisfying the product's realtime requirements.

---

## 8. PostgreSQL for Core Persistence

PostgreSQL is the authoritative store for core platform data.

This includes data such as:

- users and profile state
- friendships
- chat state
- forum posts and related discussion data

The platform design assumes relational consistency matters more than using separate persistence technologies for each service domain.

---

## 9. Backup and Recovery Design

The stack includes automated PostgreSQL backups and a documented disaster recovery runbook.

Technical decisions here include:

- backup artifacts stored in a mounted repository path
- recovery performed through SQL restore into a recreated database
- explicit production-compose recovery commands
- a tested restore flow rather than documentation alone

This supports the DevOps module with a procedure that can be demonstrated end to end.

---

## 10. Redis for Gateway Rate Limiting

Redis is used by the gateway for request-rate control.

This is a focused technical choice:

- it gives the gateway fast state management for throttling decisions
- it keeps rate-limiting state outside the gateway process
- it avoids pushing this concern into unrelated business services

The project does not currently use Redis as a general application database.

---

## 11. Prometheus and Grafana Integration

Prometheus is used to scrape metrics from the service stack, and Grafana is used for dashboards and operator visibility.

The important implementation detail is that observability is integrated into the platform rather than running entirely outside it.

Current behavior includes:

- service metrics exposure
- Prometheus scraping
- Grafana dashboards and alerts
- admin-only browser access through the gateway under `/api/admin/...`

This makes observability both demonstrable and operationally consistent with the platform's security model.

---

## 12. Container-First Runtime

The system is built to run through Docker Compose-managed services.

This affects technical choices throughout the repo:

- environment-driven runtime configuration
- service health checks
- explicit dependency ordering
- certificate and truststore mounting
- reproducible local and evaluation startup flows

The project is therefore optimized for containerized execution rather than ad hoc local process orchestration.

---

## 13. Repository Conventions

The repository uses a small set of practical conventions:

- environment examples are provided under `environment/`
- operational and architectural references are documented under `docs/` and `infra/`
- service-specific behavior is documented close to the relevant service where useful
- the root `Makefile` acts as the main operator entry point for stack lifecycle commands

These conventions help the repo stay navigable even though it spans multiple languages and services.

---

## 14. Technical Tradeoff

The core technical tradeoff is choosing platform realism over minimal implementation simplicity.

That means accepting:

- more runtime configuration
- more service boundaries
- more observability and recovery work
- more integration points

in exchange for:

- stronger isolation of concerns
- a real gateway layer
- credible DevOps and security behaviors
- a system that better reflects the selected modules

That tradeoff is intentional and visible throughout the implementation.
