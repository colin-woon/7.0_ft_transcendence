# Architectural Decisions

## Purpose

This document records the current architectural decisions behind 42 Overflow as implemented in the repository. It is intended as a public technical reference for evaluators, collaborators, and readers who need to understand why the system is structured the way it is.

---

## 1. Microservices Architecture

42 Overflow is implemented as a multi-service platform rather than a single monolith.

The current service split is:

- **Nginx** as the external HTTPS entry layer
- **Gateway Service (Quarkus)** as the centralized routing and policy layer
- **Auth Service (Quarkus)** for identity, tokens, user management, and OAuth flows
- **Forum Service (FastAPI)** for project discussions, replies, and voting
- **Chat Service (Go)** for friendships, messaging, presence, and realtime chat behavior
- **Web Service (Next.js)** for the frontend application
- **PostgreSQL** for persistent relational data
- **Redis** for gateway rate limiting
- **Prometheus** and **Grafana** for observability

This structure was chosen to preserve clear service responsibilities, allow different backend technologies where they fit best, and make the platform architecture itself part of the project value.

---

## 2. Centralized Gateway Control

The system uses a dedicated gateway rather than exposing each backend service directly to browsers.

The gateway is responsible for:

- request routing across service families
- JWT-aware authentication handling
- route-family-based RBAC
- request policy enforcement
- header shaping and trusted internal context propagation
- Redis-backed rate limiting
- stream-aware proxy behavior
- edge-level logging and metrics

This decision keeps security-sensitive and cross-cutting traffic rules in one place instead of duplicating them across every backend service.

---

## 3. Zero-Trust Service Boundaries

The platform follows a zero-trust backend model.

That means:

- external access is protected with HTTPS
- protected backend traffic is authenticated before business logic executes
- internal service calls use trusted transport and shared trust material where required
- backend services do not treat raw external request headers as authoritative identity

The gateway derives trusted request identity and forwards normalized internal context to downstream services. This reduces duplication and narrows the surface for inconsistent authorization behavior.

---

## 4. Dedicated Identity Service

Identity concerns are kept in the Auth Service rather than spread across the system.

The Auth Service owns:

- local authentication
- OAuth integration
- JWT issuance
- user profile and role state

Other services consume trusted identity context rather than independently issuing credentials or handling browser-facing auth flows.

This keeps identity issuance centralized and reduces coupling between product domains.

---

## 5. Domain-Oriented Service Separation

Each application service is aligned to a specific domain:

- **Auth Service**: identity and user management
- **Forum Service**: structured technical discussions
- **Chat Service**: friendships and direct messaging
- **Web Service**: user-facing application delivery

This separation improves maintainability and keeps the system explainable during evaluation. It also makes service-specific testing, observability, and failure handling more explicit.

---

## 6. PostgreSQL as the Primary Data Store

The platform uses PostgreSQL as the primary persistent store.

Reasons for this choice:

- the core product data is relational
- user, friendship, message, and discussion data benefit from strong consistency
- the stack needs reliable backup and recovery procedures
- the selected technologies integrate well with PostgreSQL

The current platform treats PostgreSQL as critical operational state and includes automated backups plus a documented restore workflow.

---

## 7. Redis as a Focused Support Dependency

Redis is used in a narrow, intentional role instead of as a general-purpose data store.

Its current primary use is:

- gateway-backed rate limiting

This keeps Redis operationally useful without turning it into a second primary persistence layer.

---

## 8. Observability as a First-Class Platform Concern

The project treats monitoring as part of the architecture rather than an afterthought.

The current observability model includes:

- Prometheus for metrics collection
- exporters and service integrations
- Grafana dashboards
- alerting rules
- service-health visibility for operators

Observability access is not treated as a public product surface. It is routed through the gateway under admin-only paths:

- `/api/admin/prometheus/`
- `/api/admin/grafana/`

This keeps operator tooling reachable while aligning it with the platform's RBAC model.

---

## 9. Realtime Messaging Without Turning the Whole Platform Into a Socket System

Realtime behavior is limited to the areas that need it most, especially chat and presence-related flows.

The architecture supports long-lived, realtime client behavior while keeping the rest of the product in normal request/response form. This helps the project support direct messaging without forcing every product capability into the same transport model.

---

## 10. Containerized Deployment Model

The platform is designed to run as a Docker-managed service stack.

This deployment model was chosen to provide:

- reproducible local and evaluation environments
- explicit service dependencies
- controlled runtime configuration
- integrated monitoring services
- backup and recovery procedures that can be demonstrated

This makes the system easier to evaluate as a coherent platform rather than a set of disconnected local processes.

---

## 11. Architectural Tradeoff

The main architectural tradeoff is additional operational complexity in exchange for clearer boundaries and stronger platform behavior.

Compared with a simpler monolith, this design requires:

- more service coordination
- more runtime configuration
- more observability and recovery discipline

In return, it provides:

- cleaner responsibility boundaries
- centralized traffic policy
- more realistic infrastructure concerns
- a stronger fit for the selected modules in security, DevOps, and custom gateway behavior

That tradeoff is intentional and central to the project's design.
