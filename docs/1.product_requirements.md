# Product Requirements Document (PRD)

# 42 Overflow

---

## 1. Product Scope

42 Overflow is a secure, multi-user web platform for 42 students to:

- Discuss projects in structured forums
- Communicate via real-time direct messaging
- Manage identity and roles securely
- Operate under a production-style microservices architecture

The system must satisfy all mandatory ft_transcendence requirements and selected modules while remaining within defined scope boundaries.

---

## 2. User Roles

### 2.1 Student

- Authenticate via OAuth
- View and edit own profile
- Send/accept friend requests
- Participate in forum discussions
- Send direct messages to friends
- Upvote/downvote forum posts
- Edit/delete own comments

### 2.2 Admin (Staff Role)

- All Student permissions
- CRUD access to forum content
- Role management capabilities
- Content moderation authority

Role enforcement must occur at backend level.

---

## 3. Functional Requirements

### 3.1 Authentication

- Users must authenticate via:
    - Google OAuth
    - 42 OAuth
- Upon successful authentication:
    - JWT must be issued
    - User record must be created if not existing
- All protected routes must require valid authentication.
- Expired or invalid tokens must result in 401 Unauthorized.

---

### 3.2 Profile Management

- Users must be able to:
    - View own profile
    - View other user profiles
    - Update profile information (name, bio)
    - Upload avatar image
- Avatar upload must validate:
    - File type
    - File size
- Default avatar must be assigned if none provided.

---

### 3.3 Friend System

- Users must be able to:
    - Send, accept, reject, block friend requests
    - Manage friend list:
        - View friends online status
        - Remove, block/unblock friends
        - Group friends by project or custom categories
        - Search friends by name or project association
        - Favorite friends for quick access (Optional)

- Security and privacy settings must allow users to control:
    - Who can send friend requests (e.g., unless blocked)
    - Who can see their online status (e.g., friends only, public)
    - Who can message them (e.g., friends only, friends of friends, public)

- Websocket connections:
    - Must validate authentication
    - Must respect user privacy settings for online status and messaging
    - Must handle disconnections gracefully

---

### 3.4 Forum Module

- Each 42 project must have a dedicated discussion board.
- Users must be able to:
    - Create post
    - Reply to post
    - Upvote or downvote content
    - Mention other users using @username
- Markdown must render correctly for code blocks.
- Forum does NOT require real-time updates.
- Pagination or lazy loading must be implemented.
- Admin or Moderator can delete or edit any forum content.
    - Will have a footnote indicating moderation action and the moderator's name.
- Students can only edit/delete their own content.
- Favoriting posts or threads (Optional).

---

### 3.5 Real-Time Chat Module

- Based on security options, chat may be limited to friends only or open to all users.
- Users must be able to:
    - Send direct message
    - Receive message in real-time
    - See typing indicator
    - See read receipts
    - See online/offline status
- Messages must:
    - Be persisted in database
    - Be retrievable upon reload
    - Filter out inappropriate content based on user privacy settings (Optional)
- WebSocket connections must:
    - Validate authentication
    - Handle disconnections gracefully
    - Stop typing indicators on disconnect

---

## 4. Non-Functional Requirements

### 4.1 Performance

- Chat message delivery should occur within 1 second under normal load.
- System must support multiple concurrent users.
- Forum pagination must prevent excessive load.
- Avatar uploads must be processed asynchronously to avoid blocking user actions.
- Caching strategies should be implemented for frequently accessed data (e.g., user profiles, forum threads) to improve response times.

### 4.2 Reliability

- WebSocket disconnections must not crash the service.
- Service failures must not cascade across microservices.
- Data integrity must be maintained during concurrent operations (e.g., voting, friend requests).
- Backup and recovery mechanisms must be in place for critical data (e.g., user profiles, forum posts, chat messages).
- System must handle edge cases gracefully (e.g., invalid input, network interruptions).

### 4.3 Concurrency

- Concurrent forum interactions must not cause data corruption.
- Duplicate friend relationships must be prevented.
- Rate limiting must prevent abuse.
- WebSocket connections must be managed to prevent resource exhaustion.
- Database transactions must ensure consistency during concurrent updates (e.g., voting, friend requests).

### 4.4 Observability

- Metrics must be exposed for:
    - Request rate
    - Error rate
    - Response time
    - Active WebSocket connections
- Logs must include:
    - Authentication attempts
    - Access patterns
    - Potential security incidents
    - Role-based access control events
- Health check endpoints must be available.
- Logs must not expose sensitive data.

---

## 5. Security Requirements

- HTTPS must be enforced everywhere.
- Internal services must communicate securely with mTLS.
- JWT must be validated at gateway level.
- Role-based access control must be enforced at backend.
- Rate limiting must prevent brute-force attempts.
- No secrets stored in repository.
- All inputs must be validated on frontend and backend.

---

## 6. Infrastructure Requirements

- Application must run via Docker with a single command.
- Services must be isolated in Docker network.
- Database schema must have clear relationships.
- .env file must not be committed.
- .env.example must be provided.
- Docker secrets or Vault must be used for sensitive data (e.g., database credentials, API keys).
- README must include setup instructions and architecture overview.
- Docker Compose file must define all services and dependencies.
- Health check endpoints must be defined for each service in Docker Compose.
- Services must be configured to restart on failure in Docker Compose.

---

## 7. Compliance Requirements

- Privacy Policy page must be accessible.
- Terms of Service page must be accessible.
- Pages must contain relevant content.
- No placeholder content allowed.

---

## 8. Constraints

- No feature additions outside defined modules without PO approval.

---

## 9. Definition of Done

A feature is considered complete only if:

- Backend logic implemented
- Frontend UI implemented
- Validation applied
- Security checks enforced
- Tested manually
- Demonstrable during evaluation
- Documented in README

---

## 10. Out of Scope

The following are explicitly excluded:

- Public anonymous posting
- Cross-campus federation
- AI-driven moderation
- Advanced recommendation systems
- Non-module-related enhancements
