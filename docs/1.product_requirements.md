# Product Requirements

## 42 Overflow

---

## 1. Product Goal

42 Overflow is a secure, multi-user web platform for 42 students. Its goal is to support social interaction and structured technical collaboration through:

- user identity and profile management
- friendships and direct messaging
- project-based discussion forums
- secure access control
- operational visibility through monitoring

The product must remain coherent with the `ft_transcendence` mandatory requirements and the team's selected modules.

---

## 2. Target Users

### Student

Primary end user of the platform.

Students need to:

- sign up or log in securely
- manage their profile
- add and manage friends
- participate in project discussions
- send and receive direct messages

### Admin

Administrative user with elevated permissions.

Admins need to:

- manage user roles and protected actions
- access broader moderation and platform-control capabilities
- enforce platform rules at backend level

---

## 3. Product Capabilities

### 3.1 Authentication and Identity

The product must support:

- secure email/password authentication
- remote authentication using OAuth 2.0
  - Google
  - 42
- user session continuity through token-based backend validation
- user profile visibility and update flows

Users must be able to:

- view their own profile
- view other user profiles
- update profile information
- upload an avatar

If no avatar is provided, the system must provide a default avatar path.

### 3.2 Friend and Social Features

Users must be able to:

- send friend requests
- accept or reject friend requests
- remove or block other users where supported by the product
- view friend relationships
- view relevant online-status information

These interactions must be enforced through backend rules, not only through frontend visibility.

### 3.3 Direct Messaging

The product must support direct messaging between users with realtime behavior.

Messaging capabilities include:

- send and receive direct messages
- persist chat history
- typing indicators
- read receipts
- user-profile access from the chat interface

Realtime communication must handle long-lived client connections without breaking authentication or request policy expectations.

### 3.4 Forum and Technical Discussion

The product must support structured technical discussion through project-based forum features.

Users must be able to:

- create posts
- reply to posts
- interact with discussion content through voting where enabled
- browse persistent discussion history

The forum experience should remain suited to project-specific knowledge sharing rather than unstructured chat alone.

### 3.5 Permissions and Roles

The product must enforce role-based access control at backend level.

The system must support:

- standard authenticated-user actions
- admin-only actions
- different available views or actions depending on user role

Role enforcement must not rely only on frontend page hiding.

---

## 4. Platform Requirements

### 4.1 Architecture

The application must run as a multi-service web platform with:

- a frontend service
- a gateway service
- dedicated backend application services
- persistent database storage

The platform must preserve clear service responsibilities and avoid collapsing all logic into a single monolith.

### 4.2 Gateway Responsibilities

The gateway is a core part of the product architecture.

It must provide:

- centralized request routing
- JWT-aware authentication handling
- role-based access control enforcement for protected paths
- request-policy enforcement
- rate limiting
- observability at the application edge

### 4.3 Realtime Support

The platform must support realtime user-facing behavior for chat and presence-related interactions.

The exact transport implementation may vary, but the product must provide:

- cross-client realtime updates
- graceful connection lifecycle handling
- durable behavior under normal disconnect/reconnect scenarios

### 4.4 Operational Visibility

The platform must expose operational signals suitable for service monitoring.

This includes:

- request metrics
- error metrics
- latency visibility
- health checks
- dashboard-based operator visibility

Prometheus and Grafana are the current observability tools used by the project.

Operator access to observability surfaces must remain restricted to protected administrative paths rather than general user-facing routes.

---

## 5. Security Requirements

The product must follow a secure default posture.

Required controls include:

- HTTPS for external access
- secure internal service communication where required by the architecture
- JWT validation before protected backend access
- backend-enforced RBAC
- request rate limiting
- validation of user input on frontend and backend
- no committed runtime secrets in version control

The product must treat authentication, authorization, and trusted internal context propagation as backend responsibilities.

---

## 6. Reliability and Data Requirements

The platform must preserve user and discussion data reliably.

Required behaviors include:

- persistent storage for core user, forum, and chat data
- health checks for runtime services
- backup procedures for critical data
- documented disaster recovery process
- protection against common concurrency issues in multi-user flows

---

## 7. Deployment Requirements

The platform must be runnable as a containerized application stack.

Deployment expectations include:

- Docker-based execution
- service definitions with dependencies and health behavior
- local environment configuration through `.env`-style files
- environment examples for required configuration
- monitoring services integrated into the stack

---

## 8. Compliance Requirements

The product must provide:

- an accessible Privacy Policy page
- an accessible Terms of Service page
- meaningful content rather than placeholder text

The project must also remain explainable during evaluation, including:

- architecture choices
- chosen modules
- role distribution across the team
- implementation ownership

---

## 9. Definition of Done

A product capability is considered done only when:

- backend behavior is implemented
- frontend behavior is implemented where applicable
- validation is in place
- security rules are enforced
- the behavior is testable and demonstrable
- the feature is documented clearly enough for evaluation and public understanding

---

## 10. Out of Scope

The following are outside the intended product scope unless explicitly revisited later:

- unrelated feature expansion outside selected modules
- public anonymous posting
- non-essential game-first functionality
- product features that weaken the coherence of the platform's social and collaborative direction
